## 一、核心认知：笔记数量的正确获取

### 1.1 ❌ 错误做法：直接查 DOM 计数

```javascript
// 这个方法不可靠！
document.querySelectorAll('.sider-list-item').length
// 返回 50 —— 但实际可能有 64 条
```

**为什么错**：
- biji.com 侧边栏有硬限制，最多渲染 50 条 DOM
- 这是 Vue 的虚拟列表优化，不是全部数据
- 用这个数字作为基数会导致静默丢失数据

### 1.2 ✅ 正确做法：先截图确认页面全貌

**第一步：截图看页面**
- 看页面上是否有"共 X 条"的计数器
- 看侧边栏是否显示了完整列表
- 看是否有分页组件（"下一页"/"加载更多"）

**第二步：检查博主入口**
- 如果页面有"博主"tab，点进去看博主详情
- 博主详情页会显示准确的笔记总数（如"64 条笔记"）

**第三步：对比两个视图**
- followId 视图（URL 带 `followId=xxx`）：可能有数量限制
- 博主入口视图：通常没有限制

### 1.3 实战案例

**错误路径**：
```
用户提供 URL（带 followId 参数）
→ DOM 查询返回 50
→ 我宣布"50篇笔记"
→ 实际有 64 篇
→ 用户发现少了 14 篇
```

**正确路径**：
```
用户提供 URL
→ 先截图确认页面全貌
→ 发现"博主"tab 显示"64 条笔记"
→ 确认 followId 视图有 50 条限制
→ 从博主入口进入获取全部 64 条
```

## 二、关键发现：平台的技术限制

### 2.1 侧边栏 DOM 渲染限制

**现象**：无论怎么滚动侧边栏，DOM 中最多只有 50 条笔记。

**验证方法**：
```javascript
// 设置 MutationObserver 监听 DOM 变化
const observer = new MutationObserver(() => {
  console.log('当前 DOM 条目数:', document.querySelectorAll('.sider-list-item').length);
});
observer.observe(document.querySelector('.sider-list'), { childList: true, subtree: true });

// 然后滚动侧边栏
// 观察控制台输出，看条目数是否增加
```

**结论**：这是 Vue 的虚拟列表实现，不是懒加载。50 条就是全部渲染的 DOM。

### 2.2 followId 视图的硬限制

**现象**：通过 `followId` 参数进入的知识库视图，最多只返回 50 条笔记。

**可能原因**：
- 服务端分页限制
- 前端缓存策略
- 商业逻辑（如免费版限制）

**应对策略**：
1. 如果用户给了 followId 视图的 URL，主动检查博主入口
2. 如果笔记数接近 50，提醒用户可能存在更多

### 2.3 博主入口没有限制

**现象**：通过"博主"tab 进入博主详情页，可以看到完整的笔记数量（如 64 条）。

**原因推测**：
- 博主入口使用不同的 API 端点
- 博主主页是公开信息，没有数量限制

**实践建议**：
- 如果 followId 视图显示 50 条，优先尝试博主入口
- 博主入口是获取完整笔记列表的可靠路径

## 三、API 拦截与分页参数

### 3.1 关键 API 端点

| 端点 | 用途 | 备注 |
|------|------|------|
| `follow/account/posts` | 获取关注者的笔记列表 | POST 请求 |
| `topic/post/list` | 获取单篇笔记详情 | POST 请求 |
| `topic/list/manager` | 获取知识库笔记列表（博主视图） | 支持分页 |

### 3.2 分页参数

**topic/list/manager 端点**：
```
https://knowledge-api.trytalks.com/v1/web/topic/list/manager
  ?is_selection=0
  &page=1
  &size=50
```

**参数说明**：
- `page`：页码，从 1 开始
- `size`：每页条数，默认 50
- `is_selection`：是否精选

**尝试修改 size**：
```javascript
// 理论上可以设置 size=200 一次性获取全部
// 但需要验证服务端是否接受
```

### 3.3 CORS 限制

**现象**：直接在浏览器中 fetch API 域名会被 CORS 阻止。

**原因**：
- `knowledge-api.trytalks.com` 只允许特定来源访问
- 浏览器直接请求会被同源策略阻止

**解决**：
- 不要尝试直接 fetch API
- 改用页面导航方式（打开原始笔记页提取内容）

### 3.4 认证上下文

**现象**：直接调用 API 返回 `{"message":"AppNotFound"}`。

**原因**：
- API 需要认证上下文（httpOnly cookie）
- JavaScript 无法读取 httpOnly cookie
- 即使拿到 csrfToken，也无法完整认证

**结论**：放弃 API 直接调用路线，改用页面导航方式。

## 四、批量提取的陷阱与应对

### 4.1 iframe 方案：为什么失败

**尝试**：在主页面内用 iframe 并行加载多个笔记 URL。

**失败原因**：
- iframe 无法继承主页面的登录态
- biji.com 有跨域限制
- 返回错误："当前知识库由于作者设置，不支持访问"

**教训**：
- 不要假设 iframe 能继承认证状态
- 跨域问题在 SPA 中很常见
- 先小规模测试方案可行性，再批量执行

### 4.2 localStorage 跨页面持久化：为什么失败

**尝试**：在浏览器中执行循环脚本，每次导航后自动提取并存入 localStorage。

**失败原因**：
- 页面跳转导致 JS 状态丢失
- 浏览器导航会清空当前页面的执行上下文

**教训**：
- SPA 的路由切换不等于页面跳转
- 真正的浏览器导航（navigate）会清空 JS 状态
- 需要用持久化存储（如浏览器扩展）才能跨页面保持数据

### 4.3 正确的批量提取策略

**推荐方案：逐个打开 + 逐个提取**

1. 用 `browser_open` 打开笔记 URL
2. 等待页面加载（1-2 秒）
3. 用 `browser_eval` 提取内容
4. 用 `browser_save_file` 保存到本地文件
5. 关闭当前标签，继续下一篇

**优点**：
- 每次都是独立的浏览器会话，认证状态完整
- 不受 CORS 限制
- 可靠性高

**缺点**：
- 速度慢（每篇需要打开/关闭标签）
- Token 消耗大

### 4.4 Agent 并行处理：加速方案

**方案**：用后台 Agent 并行处理多个 URL。

**实现**：
```javascript
// 主 Agent 负责协调
// 后台 Agent 负责逐个打开 URL 并提取内容
// 每个 Agent 处理一个子集（如 10 个 URL）
```

**注意事项**：
- 每个 Agent 需要独立的浏览器标签
- 需要处理并发限制（浏览器同时打开的标签数）
- 需要汇总所有 Agent 的结果

## 五、错误处理与决策框架

### 5.1 什么时候该停止尝试

**信号 1：连续 3 次相同类型的失败**
- 如果 iframe 方案失败 3 次，放弃
- 如果 API 调用失败 3 次，放弃
- 不要在同一堵墙上撞 3 次以上

**信号 2：违反基本假设**
- 如果发现 CORS 限制，不要尝试绕过
- 如果发现认证问题，不要尝试伪造
- 基本假设被推翻 = 方案不可行

**信号 3：时间/Token 消耗过大**
- 如果一个方案已经消耗了 30% 的 Token 预算，还没成功
- 如果一个方案已经执行了 10 分钟，还没看到希望
- 及时止损，换方案或报告限制

### 5.2 如何识别平台硬限制

**特征 1：数字恰好是整数（如 50、100）**
- 如果 DOM 查询恰好返回 50，很可能是硬限制
- 真实数据通常不会恰好是整数

**特征 2：滚动无效果**
- 如果滚动侧边栏后 DOM 条目数不变
- 说明不是懒加载，而是硬限制

**特征 3：不同入口显示不同数量**
- 如果 followId 视图显示 50，博主入口显示 64
- 说明是视图级限制，不是数据缺失

### 5.3 决策树：当笔记数量不匹配时

```
用户说有 64 条，DOM 只显示 50 条
│
├─ 步骤 1：截图确认页面全貌
│   └─ 页面上是否有"共 X 条"的计数器？
│
├─ 步骤 2：检查博主入口
│   └─ 博主详情页是否显示 64 条？
│   └─ 如果是 → 从博主入口进入
│
├─ 步骤 3：检查是否有分页
│   └─ 侧边栏是否有"加载更多"按钮？
│   └─ 页面是否有分页组件？
│
├─ 步骤 4：尝试修改 API 参数
│   └─ 拦截 API 请求，看分页参数
│   └─ 尝试修改 size 参数
│
└─ 步骤 5：如果以上都失败
    └─ 报告限制：这是平台的硬限制
    └─ 给出替代方案：分批提取、手动导出
```

## 六、元认知：避免重复踩坑

### 6.1 提取前的检查清单

在开始批量提取前，必须确认：

- [ ] **笔记总数**：页面上显示的总数是多少？（不是 DOM 查询结果）
- [ ] **入口来源**：是 followId 视图还是博主入口？
- [ ] **分页情况**：是否有分页组件？每页多少条？
- [ ] **认证状态**：浏览器是否已登录？能否访问完整内容？

### 6.2 提取中的监控指标

在批量提取过程中，持续监控：

- [ ] **DOM 条目数**：是否稳定？是否在增加？
- [ ] **API 请求**：是否有新的网络请求？
- [ ] **拦截器状态**：window.open 拦截器是否有效？
- [ ] **错误日志**：是否有 CORS/认证/404 错误？

### 6.3 提取后的验证清单

在交付前，必须验证：

- [ ] **数量匹配**：提取的笔记数 = 用户说的数量？
- [ ] **内容完整**：每篇笔记都有原文 + AI 总结？
- [ ] **无重复**：没有重复提取的笔记？
- [ ] **格式正确**：markdown 格式符合要求？

### 6.4 失败模式速查表

| 失败模式 | 症状 | 根因 | 正确做法 |
|----------|------|------|----------|
| 假完成 | 报告"50篇"，实际 64 篇 | DOM 查询不等于真实数量 | 先截图确认页面全貌 |
| 工具盲区 | iframe/API 反复失败 | 没有预判 CORS/认证限制 | 先小规模测试方案可行性 |
| 执行鸿沟 | 开始说"你帮我..." | 技术路径堵死后踢皮球 | 穷尽所有工具路径再报告限制 |
| 范围漂移 | 为了补 14 篇尝试了 8 种方法 | 没有及时止损 | 连续 3 次失败就换方案 |
| 过期自信 | 没读完 skill 文档就开始 | 假设自己知道怎么做 | 先读完文档再动手 |

## 七、最佳实践总结

### 7.1 提取流程优化

**传统流程**（低效）：
1. 打开页面
2. DOM 查询计数
3. 开始批量提取
4. 发现数量不对
5. 尝试补救
6. 浪费大量时间

**优化流程**（高效）：
1. 打开页面
2. **截图确认页面全貌**（关键！）
3. **检查博主入口**（关键！）
4. 确认笔记总数
5. 开始批量提取
6. 验证数量匹配
7. 交付

### 7.2 错误处理原则

**原则 1：先验证假设，再执行**
- 不要用 DOM 查询结果作为最终数字
- 先确认页面上是否有明确的计数器

**原则 2：小规模测试，再批量执行**
- 先用 1-2 篇笔记测试方案可行性
- 确认方案有效后再批量执行

**原则 3：及时止损，不要死磕**
- 连续 3 次失败 → 换方案
- 发现基本假设错误 → 重新评估
- 时间/Token 消耗过大 → 报告限制

**原则 4：给用户明确的预期**
- 如果有数量限制，提前告知
- 如果有 9 篇缺失原文，说明原因
- 不要假装"全部完成"

### 7.3 Token 优化技巧

**技巧 1：用 browser_save_file 而不是 tool result**
- 大数据量（>20 条）必须用 browser_save_file 直接写文件
- 不要把大量数据内嵌到 tool result 中

**技巧 2：用 Agent 并行处理**
- 35 篇笔记可以用后台 Agent 并行提取
- 每个 Agent 处理一个子集，最后汇总

**技巧 3：避免重复提取**
- 先提取 AI 总结（在同一页面）
- 再批量提取原文（需要逐个打开）
- 不要来回切换提取方式

## 十、经验教训总结

### 10.1 最重要的三条教训

1. **永远不要用 DOM 查询结果作为最终数字** —— 先截图确认页面全貌

3. **及时止损，不要死磕** —— 连续 3 次失败就换方案

### 10.2 避免重复踩坑的检查清单

在开始新的 biji.com 提取任务前，回顾这个清单：

- [ ] 我是否确认了笔记总数？（不是 DOM 查询结果）

- [ ] 我是否测试了方案可行性？
- [ ] 我是否设置了错误处理机制？
- [ ] 我是否准备了替代方案？

- 不要直接开始工作
